# `polar_plotting` receives only a composed angle sign, never rotation direction or measurement convention

`polar_plotting` must stay domain-agnostic and liftable into other projects (see `CLAUDE.md`'s architecture table), but the app needs two separate, learner-facing toggles — rotation direction (CW/CCW) and measurement convention (with/against rotation) — to teach how they combine. We decided `polar_plotting` never sees either toggle individually: `ui` composes them (`angle_sign = rotation_direction × measurement_convention`) and passes only the single resulting `angle_sign`, alongside `zero_direction`, as its angle convention.

We considered instead giving `polar_plotting` both raw toggles directly, which would have made its API slightly more self-explanatory at the call site. We rejected it because it would leak two domain-flavored concepts into a module whose whole purpose is to have none — a future consumer embedding `polar_plotting` elsewhere would have to either adopt this app's rotation/measurement vocabulary or fake it. Composing in `ui` keeps `polar_plotting`'s contract to two plain numbers with no interpretation attached, and also guarantees rotation-direction changes and angle-label renumbering can't drift out of sync with each other, since the sign is always derived, never set independently in two places.
